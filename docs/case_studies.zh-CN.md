# 看似正确，实则有误

[English](case_studies.md) · 简体中文

缓存注意力掩码可能形状正确，含义却是错的。经过审计的结果可能复现了记录中的计算，却建立在有缺陷的输入数据上。这些案例展开说明 README 中的[我构建了什么](../README.zh-CN.md#what-i-built)和[改变我结论的两个转折点](../README.zh-CN.md#two-moments-that-changed-my-conclusions)。文末的开发试验则补充了[尝试过但没有成功的方法](../README.zh-CN.md#things-i-tried-that-didnt-work)的背景。

<a id="checking-cached-attention"></a>

## 检查缓存注意力

<a id="the-problem"></a>

### 问题

KV cache 保存先前的键和值，供后续生成复用。新的一块输入到来时，注意力掩码必须反映它在累计上下文中的绝对位置。

设想已经缓存了三个位置，再加入两个新查询。第一个查询位于位置 3，可以关注位置 0 至 3 的键；第二个查询位于位置 4，可以关注全部五个键。通用的左上对齐三角掩码形状正确，但允许关注的位置不对：它把两个查询当成从位置 0 开始，只让它们看到前 1 个和前 2 个键，本应可见的缓存位置被遮住了。

<a id="the-implementation-and-check"></a>

### 实现与检查

我实现的注意力封装区分三种输入：初始输入、单 token 解码，以及追加到已有上下文的多 token 块。实现使用绝对 RoPE 位置、预分配的 KV 存储和请求级事务，缓存会检查位置与容量。如果部分层已经追加了数据、模型调用随后失败，模型会先恢复原先可见的缓存长度，再允许下一次调用。

手算核查测试把所有查询和键置零，使允许位置上的注意力权重均匀分布。值为 `[1, 2, 3, 4, 5]` 时，预期输出是 **2.5 和 3.0**；使用错误掩码则输出 **1.0 和 1.5**。这种方法不依赖模型的随机行为，就能直接暴露对齐错误。

其他测试覆盖不等长的输入块，以及在后续注意力层注入故障的情况。回滚测试同时检查缓存长度是否恢复，以及随后的一次调用是否正确。

<a id="streaming-tokenization-must-preserve-the-token-sequence"></a>

## 流式分词必须保持 token 序列不变

分块只是输入的传输方式，不能改变 token ID。用测试中的 GPT-2 词表和合并规则，`encode("we're")` 返回 `[732, 821]`。早期的流式实现对 `["we'r", "e"]` 却输出 `[732, 6, 260]`，尽管解码后的文本相同。[分词器](../src/cs336_basics/tokenizer.py)只输出边界已经确定的前缀，把末尾还可能和下一块合并的预分词片段留到下一块一起处理。[回归测试](../tests/test_tokenizer.py)把整段编码与每一种二分切块、逐字符输入的结果相比较，覆盖缩写、空白、Unicode 和相互重叠的特殊 token。

<a id="restoring-training-state-not-only-weights"></a>

## 恢复训练状态，而不只是权重

训练与验证使用各自独立的 NumPy 随机数生成器。版本 2 检查点保存优化器与随机数生成器的状态，训练入口在恢复前会核查数据内容和实际生效的配置。[现有测试](../tests/test_training_reproducibility.py)用真实的小型 Transformer 和优化器，比较连续训练与中断后恢复训练的轨迹，并检查改变评估频率不会改变训练样本。[序列化测试](../tests/test_serialization.py)覆盖检查点接口。

<a id="a-data-defect-that-flipped-the-primary-result"></a>

## 翻转主要结果的数据缺陷

**现象。** 一些已保存的程序通过了记录中的全部隐藏测试，却在公开样例上发生运行错误。在 Qwen3 的 LiveCodeBench Pro（下文简称 LCB Pro）记录中，受影响的是 **N 17/146** 和**探测草稿 58/2,405**。这种不一致需要调查，不能据此直接把程序改判为正确。

**定位。** 空行原本就存在于上游 Hugging Face parquet 的 `problem_statement` 字段中，不是本地提取时加进去的。全部 **78/78** 个公开输入都呈现完全相同的序列化模式：开头一个 LF，非空数据行之间两个 LF，结尾两个 LF。这把缺陷定位到了上游字段。[来源追踪](../runs/lcb_public_erratum/summary.json)

**修正。** 修复只逆转这一确切模式：去掉开头的 LF，把数据行之间和末尾恢复为一个 LF，其余内容都不改。[候选规则](../runs/lcb_public_erratum/summary.json)、[已核实的修正与边界](../runs/lcb_public_erratum/official_html_v3/verification_receipt_v3.json)

**验证。** 证据分阶段积累：

- 作者测试包只能验证 **3 道题和 5 个样例**，其余 **70 道题和 73 个样例**当时为 **UNKNOWN**。[作者测试包核验](../runs/lcb_public_erratum/summary.json)
- 之后我对照 Codeforces 官方 HTML 核验。初版解析器把**每个样例都判为 UNKNOWN**：它没有实现 HTML5 中“忽略 `pre` 起始标签后第一个 LF”的规则，还把输出末尾的空格当成了冲突。
- 解析器修好后，`html5lib` 和独立的 `HTMLParser` 实现结果一致，覆盖 **73/73 道题和 78/78 个样例**。修正后的 **78/78** 个输入都与官方解析结果逐字节相同；全部 **78/78** 个原始输出按空白切分后逐字段一致，其中 **8 个样例**只有行尾空白不同。[官方 HTML 核验](../runs/lcb_public_erratum/official_html_v3/verification_receipt_v3.json)

**对照。** 同样的“公开样例失败、隐藏测试通过”现象，在 AtCoder 上却是另一回事。全部 **19 条记录（N 2 条、探测草稿 17 条）**都是真正的错误答案，只是隐藏测试没有检出。以 `abc398_d` 为例，一个可以手算核查的反例正确输出为 `0001101011`，错误程序却输出 `0000001000`：它只跟踪初始烟团，漏掉了后续生成的烟。公开样例本身没有问题，所以我没有把 LCB Pro 的修正推广到 AtCoder。

**来源核对。** 四个样本的全部 63 道题、165 个公开样例的输入／输出与原始 `test6.jsonl` 字段逐字相同（只去掉了 `testtype` 元数据）。上述两道题共 6 个样例又与官方 HTML 样例做了核对：只对 HTML 转义、CRLF 和结尾换行做展示层处理后，输入输出逐字一致，没有前置或行间空行。官方来源：[abc398_d](https://atcoder.jp/contests/abc398/tasks/abc398_d?lang=en)、[arc195_a](https://atcoder.jp/contests/arc195/tasks/arc195_a?lang=en)。

**可核查的反例。** `abc398_d` 样例 2 的正确输出是 `0001101011`；两个 N 程序以及另外 9 份探测草稿的已有缓存输出为 `0000001000`。它们只在初始烟团到达目标时输出 1，忽略了后续新生的烟：例如第 4 步时，时刻 1 新生的烟已经到达目标，而初始烟团还没有到达。另外 4 份反序的探测草稿连样例 1 也答错了。`arc195_a` 样例 2 为 `A=[1,2,1]`、`B=[1,2]`，只有位置 `(1,2)` 一个匹配，应该输出 `No`；4 个程序都输出 `Yes`，原因是错误地把末尾的 `1` 当作可用的替代，而它后面已经没有 `2` 了。缓存中这 19 次失败都正常退出、标准错误输出为空，所以不属于运行、权限、超时或比较器空白问题。

**为什么隐藏测试仍然通过。** 当前数据集中每道题只有 40 条隐藏测试，而且这 6 个公开样例都不在对应的隐藏测试输入里。`abc398_d` 的 40 个预期输出中，38 个全是 0，另外 2 个含 1 的输入长度都是 1，没有覆盖样例揭示的持续生烟错误。`arc195_a` 的隐藏测试预期输出为 37 个 No、3 个 Yes，现有的 4 个错误程序在全部 40 条上都通过。

**统一重评。** 我没有重新生成模型输出，提示词也仍是原来的。公开样例检查、最终标签、策略回放和统计都对所有策略统一更新。隐藏测试的观测按确切的缓存身份复用，并没有重新执行每一项隐藏测试（[重评范围](execexit/REPORT.zh-CN.md#lcb-pro-public-input-defect-and-correction)）。原先 **17 个 N** 和 **58 份探测草稿**在公开样例上的运行错误全部消失，这些程序都通过了最终评估。没有新增受损题，也没有新增 UNKNOWN 结果。

<a id="evaluating-faster-code-generation"></a>

## 评估更快的代码生成

<a id="the-question-and-comparison"></a>

### 问题与比较

短探测能否识别推理模型应当停止思考的时机，在保持程序成功交付的同时更早给出答案？

我在 RTX 5090 上用未修改的 vLLM 0.26.0 运行 Qwen3-8B，在来自 18 场比赛、此前已经见过的同一批 36 道开发题上比较三种方法：

- **原生推理（N）：** 不使用提前退出探测的参照路径。
- **无门控提前退出（S）：** 在第一个符合条件的机会直接接受探测结果。
- **置信度门控提前退出（D）：** 只有同一次探测的得分超过冻结阈值时才接受，否则恢复推理，不再寻找第二次探测机会。

所有方法共享 16,384 token 的总预算和相同的输出协议。丢弃的探测 token 和控制 token 都计入预算。原生方法走普通执行路径，不承担额外的探测成本。这个组件借鉴了 DEER 式探测，没有实现完整的 DEER 系统。

<a id="measuring-the-actual-outcome"></a>

### 测量实际结果

一次运行要判为成功，选定的最终响应必须以模型的序列结束标记正常结束，正确的程序必须送达客户端，并通过冻结的公开样例与隐藏测试。预算耗尽不算正常结束。所有计划中的运行都保留在分母中。

交付时间从请求准入开始，到独立的本地客户端进程收到结果为止，包含准入后的探测、恢复、处理和交付。模型加载、准入前的缓存重置、客户端进程启动等共享准备工作单独记录。多次 A/A 检查用于估计运行波动。这是一项串行比较。

<a id="results-and-decision"></a>

### 结果与判定

| 方法 | 成功交付数 | 平均交付时间 | 交付时间第 95 百分位数 |
|---|---:|---:|---:|
| 原生推理（N） | 19 / 36 | 110.08 秒 | 182.53 秒 |
| 无门控提前退出（S） | 13 / 36 | 65.83 秒 | 182.17 秒 |
| 置信度门控提前退出（D） | 14 / 36 | 90.11 秒 | 182.57 秒 |

相对原生推理，置信度门控把平均时间降低了 18.14%，但总成功数少了 5 个；按题配对后，救回 1 道题、损害 6 道题。相对无门控提前退出，门控多了 1 个成功结果，同时平均时间增加了 36.89%。

置信度规则拒绝了 17 次探测。在这些题中，13 道在两种探测方法下都失败，3 道都通过，1 道被门控救回。相对无门控提前退出，这些拒绝决策在对应的配对运行上一共多花了 874.01 秒。离线分析显示，相对无门控多出的那一个成功结果对输出提取协议敏感，不能归功于置信度门控。

两种提前退出策略都没有达到冻结的验收标准。我保留了原生推理，并结束了对这一组件的考察。这些结果说明必须测量完整结果和控制决策的实际成本。
